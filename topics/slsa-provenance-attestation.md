# SLSA & Build Provenance Attestations

<p class="lede">Knowing what dependencies are inside a software artifact (via an SBOM) is only half of the software supply chain puzzle. The second question is: how was this artifact built, and was the build platform tampered with? Supply-chain Levels for Software Artifacts (SLSA) provides a specification for build integrity. SLSA establishes verifiable build provenance attestations—using in-toto schemas—to prove that a specific binary was generated by a trusted, isolated build platform from a specific source commit.</p>

## SLSA v1.2 Build Track Levels

The **SLSA v1.2 specification** organizes build integrity into graduated levels:

| SLSA Level | Build Track Requirements | Security &amp; Integrity Guarantee |
|---|---|---|
| **SLSA Build Level 0 (L0)** | No requirements. | No build integrity or provenance guarantees. |
| **SLSA Build Level 1 (L1)** | Provenance exists and is distributed to consumer. Build process is documented. | Protects against accidental software misconfiguration; provides basic build tracking. |
| **SLSA Build Level 2 (L2)** | Provenance is **authentic and verifiable** (signed by build platform). Build runs on a **hosted build platform**. | Prevents post-build artifact tampering; guarantees build occurred on hosted infrastructure rather than a developer laptop. |
| **SLSA Build Level 3 (L3)** | Build platform enforces **hardened builder isolation** between build steps and prevents unauthorized external influence. | Prevents cross-job contamination, build runner tampering, and unauthorized external network modifications. |

*Note*: Always specify both the track and version when declaring compliance (e.g. `SLSA Build L3 (v1.2)`).

## in-toto Provenance JSON Schema

SLSA provenance is formatted as an **in-toto attestation predicate**. It links a output artifact cryptographic hash (`subject`) to the exact build parameters and platform identity (`builder`):

```json
{
  "_type": "https://in-toto.io/Statement/v1",
  "subject": [
    {
      "name": "release-binary-linux-amd64",
      "digest": {
        "sha256": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
      }
    }
  ],
  "predicateType": "https://slsa.dev/provenance/v1",
  "predicate": {
    "buildDefinition": {
      "buildType": "https://actions.github.com/workflow@v1",
      "externalParameters": {
        "workflow": {
          "ref": "refs/heads/main",
          "repository": "https://github.com/example/repo",
          "path": ".github/workflows/build.yml"
        }
      },
      "resolvedDependencies": [
        {
          "uri": "git+https://github.com/example/repo@refs/tags/v1.2.0",
          "digest": {
            "gitCommit": "4f8a923b7c50188cabbfb72cf0fd9fe288364bc4"
          }
        }
      ]
    },
    "runDetails": {
      "builder": {
        "id": "https://github.com/actions/runner@v1"
      }
    }
  }
}
```

## Hermetic & Reproducible Builds

Achieving SLSA Build L3 requires enforcing build environment isolation:

- **Hermetic Builds**: Build steps run in a network-isolated environment where all dependencies (*compilers, libraries, header files*) are explicitly declared, pinned, and fetched into local build caches before execution begins. No undeclared external network calls are permitted during compilation.
- **Reproducible Builds**: Two independent builds executed from the exact same source commit and build environment produce byte-for-byte identical binary outputs ($H(\text{Build}_1) == H(\text{Build}_2)$).

## The Boundary of SLSA: Provenance vs. Source Integrity

A critical security distinction must be maintained when evaluating SLSA guarantees:

$$\text{SLSA Provenance} \implies \text{Proves } \mathbf{HOW} \text{ an artifact was built by a specific builder from source } S.$$

$$\text{SLSA Provenance} \;\cancel{\implies}\; \text{Proves that source } S \text{ or its dependencies are } \mathbf{BENIGN}.$$

As demonstrated by the xz-utils backdoor (CVE-2024-3094), if a trusted maintainer commits malicious code into source $S$, SLSA Build L3 will faithfully compile the malicious code and generate valid, signed provenance. SLSA guarantees build integrity, not source code intent.

## Essential SLSA Diagnostic Checklist

When auditing software build pipelines for SLSA compliance, evaluate these 6 criteria:

| Diagnostic Area | Architectural Evaluation Question | Verification &amp; Audit Evidence |
|---|---|---|
| **SLSA Level Declaration** | Is the build target evaluated against explicit SLSA v1.2 Build track levels (L1, L2, L3)? | Organization SLSA compliance audit record. |
| **Authentic Signed Provenance** | Is in-toto provenance generated and cryptographically signed by the hosted build platform? | Signed in-toto JSON attestation files &amp; public key/cert checks. |
| **Hosted Builder Enforcement** | Are release builds restricted to hosted build infrastructure, blocking developer laptop builds? | CI/CD pipeline triggers &amp; runner execution logs. |
| **Verification Gate Deployment** | Do deployment environments verify artifact hashes against signed provenance prior to execution? | Kubernetes admission controller rules (Cosign/Kyverno policy). |
| **Hermetic Build Network Locks** | Are build steps isolated from external internet access during compilation (Hermetic builds)? | Build runner network container isolation rules. |
| **Dependency Commit Pinning** | Are all build tools and upstream dependencies pinned to immutable cryptographic commit hashes? | Build definition files (`build.yml`, Dockerfile `FROM sha256:...`). |
