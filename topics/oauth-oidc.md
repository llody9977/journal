# OAuth & OpenID Connect

<p class="lede">OAuth 2.0 and OpenID Connect (OIDC) govern delegated authorization and federated identity across distributed applications. OAuth 2.0 (RFC 6749) grants third-party clients scoped, time-limited access to APIs via Access Tokens, whereas OpenID Connect adds an identity layer that authenticates users via signed JSON Web Tokens (ID Tokens).</p>

## Delegated Authorization vs Identity Authentication

| Dimension | OAuth 2.0 (Authorization) | OpenID Connect (Authentication) |
|---|---|---|
| **Core Question Answered** | *What API resources is this client allowed to access?* | *Who is the authenticated user operating this client?* |
| **Primary Token Produced** | **Access Token** (a credential representing a specific, limited authorization grant, per RFC 6749; commonly implemented as an opaque string or a signed JWT using any algorithm the authorization server supports, e.g. RS256, ES256, HS256) | **ID Token** (Signed JWS container format) |
| **Token Intended Audience** | **Resource Server (API Gateway)** | **Client Application (Relying Party)** |
| **Core RFC Standard** | RFC 6749 / RFC 6750 / RFC 7636 | OpenID Connect Core 1.0 (built on RFC 7519 JWT) |

## The Four Standard OAuth 2.0 Roles

1. **Resource Owner**: The user granting access to protected data.
2. **Client**: The application (Web SPA, Mobile App, Server-side App, CLI) requesting access on behalf of the Resource Owner.
3. **Authorization Server (AS)**: The identity platform (Okta, Auth0, Keycloak, Azure AD) that authenticates the Resource Owner and issues tokens.
4. **Resource Server (RS)**: The API backend hosting protected resources and verifying Access Token claims.

## Modern Standard: Authorization Code Flow with PKCE (RFC 7636)

The **Authorization Code Flow with PKCE (Proof Key for Code Exchange)** is mandatory for public clients (SPAs, Mobile Apps) per the OAuth 2.0 Security Best Current Practice ([RFC 9700](https://datatracker.ietf.org/doc/html/rfc9700)), and RFC 9700 additionally recommends it for confidential clients as defense-in-depth against authorization code injection:

### PKCE Verification Mechanics (RFC 7636)

- **Code Verifier**: A cryptographically random string $V \in [43, 128]$ characters generated by the client.
- **Code Challenge**: The SHA-256 hash of the verifier: $\text{Challenge} = \text{Base64URL}(\text{SHA-256}(V))$.
- **Server Validation**: The Authorization Server receives $V$ at the token endpoint, computes $\text{Base64URL}(\text{SHA-256}(V))$, and asserts equality with the initial $\text{Challenge}$. Intercepted authorization codes cannot be exchanged without the secret verifier $V$.

## Anatomy of a Signed JSON Web Token (JWT / JWS)

JSON Web Tokens (RFC 7519) consist of three Base64URL-encoded segments separated by periods:

$$\text{JWT} = \text{Header} \,.\, \text{Payload} \,.\, \text{Signature}$$

```python
# jwt_demo.py: Decoding and verifying a JWS HMAC-SHA256 signature
import json, base64, hmac, hashlib

def b64url_encode(data): return base64.urlsafe_b64encode(data).rstrip(b'=')
def b64url_decode(s): return base64.urlsafe_b64decode(s + b'=' * (-len(s) % 4))

# 1. Create a signed JWS token (HS256)
secret = b"production-signing-secret"
header = b64url_encode(json.dumps({"alg": "HS256", "typ": "JWT"}).encode())
payload = b64url_encode(json.dumps({
    "iss": "https://auth.example.com/",
    "sub": "user_12345",
    "aud": "my-api-client",
    "exp": 1753003600
}).encode())

signing_input = header + b"." + payload
signature = b64url_encode(hmac.new(secret, signing_input, hashlib.sha256).digest())
token = (signing_input + b"." + signature).decode()

# 2. Inspect decoded header and payload (Publicly readable!)
h_b64, p_b64, sig_b64 = token.split(".")
print("Decoded Claims:", json.loads(b64url_decode(p_b64.encode())))

# 3. Verify Signature Integrity
calc_sig = b64url_encode(hmac.new(secret, (h_b64 + "." + p_b64).encode(), hashlib.sha256).digest())
print("Signature Valid:", hmac.compare_digest(calc_sig.encode(), sig_b64.encode()))
# Output: Signature Valid: True
```

<div class="callout warn">
  <span class="callout-title">JWT Base64 Encoding is Not Encryption</span>
  <p>JWS tokens are signed, not encrypted. Any client or network observer can decode the Base64 payload instantly. Never place raw passwords, PII, or unencrypted secrets inside JWT payload claims unless using JSON Web Encryption (JWE / RFC 7516).</p>
</div>

## Critical Security Checklist

1. **Enforce PKCE**: RFC 9700 makes PKCE mandatory for public clients and recommends it for confidential clients; deploy it across all authorization code flows.
2. **Validate State Parameter**: Enforce cryptographically random `state` parameters to prevent Cross-Site Request Forgery (CSRF) during authorization redirects.
3. **Verify Access Tokens on Resource Servers**: Validate each access token according to its format and the authorization-server profile. For JWT access tokens, verify the signature and allowed algorithm plus every required claim, commonly including `iss` (Issuer), `aud` (Audience), and `exp` (Expiration). Reject JWT access tokens that use any algorithm or protection mode the applicable profile does not allow.
4. **Never Send ID Tokens to Resource Servers**: ID Tokens belong to the Client application; Access Tokens belong to the Resource Server API.

<div class="callout">
  <span class="callout-title">What I need to remember</span>
  <p>OAuth 2.0 is an authorization framework; OpenID Connect adds authentication and ID tokens. Use Authorization Code + PKCE—required for public clients and recommended for confidential clients by RFC 9700—and do not use the implicit grant for new clients. A resource server must validate an access token according to its format and authorization-server profile; for JWT access tokens, verify the signature and algorithm plus all required issuer, audience, time, and authorization claims.</p>
</div>
