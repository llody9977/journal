# Software Supply Chain Security: SBOM, CI/CD & SLSA

<p class="lede">A production artifact normally contains application code, third-party components, and output from a build pipeline. Two separate questions need answering: what is in this artifact, and what evidence shows how it was built? An inventory answers the first; provenance and pipeline controls help with the second.</p>

## SBOM: what's actually in the build

A Software Bill of Materials answers the first question: it is a machine-readable inventory of components and their supply-chain relationships for a particular software build or product. [NTIA's 2021 minimum elements](https://www.ntia.gov/report/2021/minimum-elements-software-bill-materials-sbom) established seven baseline data fields:

1. **Component name**
2. **Component version**
3. **Component supplier**
4. **Dependency relationship** (what depends on what, upstream)
5. **Other unique identifiers** (e.g. package URLs, hashes)
6. **SBOM author** (who generated this record — not the component's author)
7. **Timestamp**

CISA published a broader **2025 draft** that renames supplier to producer and proposes component hashes, license information, tool name, and generation context. Because that document was issued for comment, the final 2021 baseline stays distinct from the proposed update rather than merging them into one mandatory list.

Two formats dominate in practice, and they come from different starting points: **SPDX**, a Linux Foundation project since 2010 and now the ISO/IEC 5962:2021 international standard, was built license-and-provenance-first; **CycloneDX**, which started inside OWASP in 2017, was built security-first and natively carries vulnerability data alongside component data. NTIA's minimum elements are deliberately format-agnostic, and CISA accepts both — the choice usually comes down to whether the immediate driver is license compliance (SPDX's original strength) or vulnerability management (CycloneDX's).

An SBOM by itself does not secure anything. Its value appears when a component issue is disclosed: a current, build-specific inventory makes it possible to search affected products systematically. Vulnerability intelligence, ownership, and a response process are still required to decide whether the component is reachable, exploitable, and remediated.

## CI/CD: where the build itself becomes the attack surface

Once dependencies are tracked, the second question is whether the pipeline that pulls them together and produces a build artifact can itself be trusted or tampered with. [OWASP's Top 10 CI/CD Security Risks](https://owasp.org/www-project-top-10-ci-cd-security-risks/) (2022) names the recurring failure modes, drawn directly from real incidents:

| | Risk |
|---|---|
| CICD-SEC-1 | Insufficient Flow Control Mechanisms |
| CICD-SEC-2 | Inadequate Identity and Access Management |
| CICD-SEC-3 | Dependency Chain Abuse |
| CICD-SEC-4 | Poisoned Pipeline Execution (PPE) |
| CICD-SEC-5 | Insufficient PBAC (Pipeline-Based Access Controls) |
| CICD-SEC-6 | Insufficient Credential Hygiene |
| CICD-SEC-7 | Insecure System Configuration |
| CICD-SEC-8 | Ungoverned Usage of 3rd-Party Services |
| CICD-SEC-9 | Improper Artifact Integrity Validation |
| CICD-SEC-10 | Insufficient Logging and Visibility |

The list is grounded in named incidents, not hypotheticals: the 2020 compromise of SolarWinds' own build system, used to distribute malware to roughly 18,000 customers; the Codecov breach, which exfiltrated secrets sitting in build-pipeline environment variables across thousands of pipelines; and a backdoored PHP release pushed through a compromised source repository. Every one of these is a build system or a credential inside it being trusted more than it should have been — not a flaw in any single dependency's code.

CI/CD pipelines are also where [Security Token Service]({{ '/topics/security-token-service/' | relative_url }}) patterns help. A pipeline can exchange its workload identity for short-lived cloud credentials instead of storing a static cloud access key. This reduces one credential-theft path; it does not remove other pipeline secrets, excessive permissions, or the risk of an attacker obtaining a valid short-lived token during a compromised run.

## SLSA: levels of build integrity

[SLSA v1.2](https://slsa.dev/spec/v1.2/) (Supply-chain Levels for Software Artifacts) separates security into tracks. In the Build track, L0 has no requirements; L1 requires provenance to exist and be distributed, generated by a hosted build platform rather than an individual workstation (it does not require the build itself to run from an automated script — that producer requirement was removed in the v1.0 specification); L2 additionally requires that provenance be authentic and verifiable, with SLSA recommending — not mandating — a digital signature as the mechanism; and L3 requires the build platform isolate build steps from unintended external influence, which is a narrower guarantee than a fully hermetic (network-isolated) build. Both the track and version should be named — such as `SLSA Build L3 (v1.2)` — because “SLSA level” by itself becomes ambiguous as the specification evolves. Provenance helps verify how an artifact was built; it does not prove that the source code or dependency was benign.

## Real-world case: the xz-utils backdoor (CVE-2024-3094)

In late March 2024, Andres Freund investigated unusual `sshd` CPU use, latency, and Valgrind errors on Debian unstable and found a backdoor in the XZ/liblzma 5.6.0 and 5.6.1 release artifacts. Under specific build and runtime conditions, the malicious library interfered with `sshd` authentication through the systemd-linked dependency path and could enable unauthorized remote access. Installing an affected XZ version alone did not make every system exploitable; distribution packaging and linkage mattered.

The important supply-chain detail is that the release tarballs contained build logic and payload material that a normal source checkout did not fully expose. That weakened the value of reviewing only the repository. The issue was found through investigation of unexpected runtime behavior, before the affected packages reached most stable distributions.

The controls answer different questions. An SBOM can show that XZ 5.6.x is present after the issue is known. SLSA provenance can show which source and builder produced an artifact and make some build tampering detectable. Neither proves that trusted source is benign. Review, separation of duties, reproducible or independently verified builds where practical, and monitoring for unexpected behavior are still required.

## Common pitfalls

- **Generating an SBOM once and never regenerating it** — a stale SBOM from six months ago doesn't reflect the dependencies actually in production today; it needs to be produced as part of every build, not as a one-time compliance exercise.
- **Treating SBOM possession as vulnerability management** — an SBOM tells you what's present; something still has to cross-reference it against current CVE data on an ongoing basis for it to do anything.
- **Assuming a scanner would have caught xz-utils** — it was hand-planted by a trusted maintainer through the legitimate release process; this is precisely the class of attack dependency scanners and SBOMs are not designed to catch.
- **Long-lived cloud credentials sitting in CI/CD secret stores** — exactly [CICD-SEC-6](https://owasp.org/www-project-top-10-ci-cd-security-risks/), and exactly what OIDC-federated, short-lived credentials via a cloud STS are built to eliminate.
