No error was raised

AES-CBC decryption always succeeds on any ciphertext that's a multiple of the block size — there is nothing in the algorithm that can detect this tampering. The application only finds out something is wrong if it later tries to parse isadmin=1 and treats it as truth, or if a separate integrity check (a MAC, or AEAD like GCM) is layered on top and rejects the message first.

Why block 2 came through untouched

This flip modified the IV, not any ciphertext block. Block 1's plaintext is D(C1) XOR IV — so the IV change garbles block 1 exactly as expected. But block 2's plaintext is D(C2) XOR C1, and C1 was never touched. Attacking through the IV affects only the first block, with zero collateral damage anywhere else.

{% else %}
The collateral damage is the tell

{{ result.touched_block_label }} decrypts to unrecoverable noise — that's the price of controlling the next block. In this token format nothing ever reads block 1 back out, so the damage is invisible to the application. A real design would put something the app actually checks in the sacrificed block, which is exactly what a MAC or GCM tag is for.

{% endif %}
Why this is a real bug class, not just a puzzle

MITRE tracks the root cause as CWE-353: Missing Support for Integrity Check. Once an application trusts a value recovered this way for an authorization decision, it becomes CWE-807: Reliance on Untrusted Inputs in a Security Decision — the well-known privilege-escalation shape. The isadmin field used here is deliberately the same one from Cryptopals Set 2, Challenge 16, a standard teaching exercise for this exact chain — this lab demonstrates the underlying integrity failure, not a ready-to-run exploit against any particular system.
