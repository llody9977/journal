CTR nonce reuse: the two-time pad

AES-CTR turns the block cipher into a keystream generator: the same key and nonce always produce the exact same keystream, XORed onto whatever plaintext you give it. Reuse that key+nonce pair for a second message, and the keystream cancels out the moment the two ciphertexts are XORed together — no key required, no cryptanalysis, just XOR.

Scope of this demo

Two short ASCII messages, deliberately encrypted with the same key and nonce — the one thing CTR mode can never tolerate. Use a throwaway random key and nonce, never real ones, and never reuse a nonce in anything real.

1Get a key and nonce

AES-128-CTR needs a 16-byte key and a 16-byte nonce (the full initial counter block, same size as openssl's -iv for CTR mode).

2Encrypt two different messages with the same key and nonce

This is the mistake the whole lab hinges on: two different plaintexts, but no new nonce for the second one.

1. Write each message to its own file:

printf '%s' '<message A>' > pA.bin
printf '%s' '<message B>' > pB.bin

2. Encrypt both with the same key and the same nonce:

openssl enc -aes-128-ctr -K <key> -iv <nonce> -in pA.bin -out cA.bin
openssl enc -aes-128-ctr -K <key> -iv <nonce> -in pB.bin -out cB.bin

The server encrypts both messages with the key and nonce above, using the same nonce for both on purpose.

What comes next

Once both ciphertexts exist, the next screen is the attack: XOR them together, then peel off one message's plaintext to recover the other's — using only the ciphertexts, never the key.
